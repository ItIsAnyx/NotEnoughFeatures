## Назначение файлов

- **app/domain.py** - структуры данных: узлы, рёбра, порты, ошибки

- **registry.py** - каталог известных блоков и их настроек

- **validation.py** - проверка графа и совместимости портов

- **golden_path.py** - построение одного заранее заданного примера графа

- **main.py** - HTTP-эндпоинты

---

### domain.py

`ContractModel` - Родительский класс для всех последующих классов. В нём указан запрет на неизвестные поля и возможность использовать Python-имя и его внешний псевдоним, например, `block_type` в Python и `"blockType"` в JSON API

`WorkflowNode` - Описывает узел:

- У узла есть свой уникальный `id`
- Ссылка на вид блока из каталога (`block_type`)
- Версия блока (`block_version`)
- `config` - настройки данного экземпляра узла. Пока что поддерживает свободную структуру словаря. Для конкретного блока структуру конфига проверяет валидатор
- `label`, `position`, `group` - информация для будущего графового редактора

`WorkflowEdge` - Задаёт связь между узлами по id узла-источника и порту и id узла-получателя и его порту. Не имеет собственный id, в диагностике используется его индекс из списка

`Workflow` - Объединяет узлы и рёбра, добавляя ID, имя схемы и её версию. Содержит в себе списки всех узлов и связей

`Port` - Центральная структура для проверки соединений:

- Хранит объявленный тип данных (`type`), например, `TabularDataset` или `Predictions`
- `cardinality` описывает количество значений внутри порта. Может быть `"single"` или `"collection"`
- `required` - определяет, нужен ли подключённый вход для узла
- `capabilities` - описывает свойства выходных данных (например, `{"modality": "tabular", "features": ["numeric"]}`)
- `requires` - описывает требования на вход (например, `{"task": "binary_classification", "hasTarget": True}`)

Два порта могут иметь одинаковый базовый тип, например, TabularDataset, но быть несовместимыми по `capabilities` и `requires`

`BlockDefinition` - объединяет идентификатор типа блока, версию, название, описание, категорию, схему настроек, словари входных и выходных портов.

- Ключом словаря является имя порта, например `{"dataset": Port(type="TabularDataset", capabilities={"hasTarget": True})}`
- `execution_supported` - явно сообщает клиенту, что выполнение данного блока ещё не реализовано.

`Diagnostic` - описывает одно сообщение проверки совместимости. Содержит в себе тип предупреждения, код ошибки, текстовое описание ошибки, UUID узла, индекс ребра, имя порта и путь до ошибочной настройки

`ValidationResult` - содержит общий флаг valid, список диагностик и допустимый порядок обхода узлов

### registry.py

Описывает Pydantic-модели настроек для всех имеющихся блоков:

| Модель | Настройки |
|---|---|
| `DatasetConfig` | Пока только фиксированное имя встроенного датасета |
| `TargetConfig` | Непустое имя target |
| `LogisticConfig` | Максимум итераций и положительный параметр `c` |
| `ForestConfig` | Число деревьев и необязательная максимальная глубина |
| `EmptyConfig` | Отсутствие пользовательских настроек |

`BlockSpec` - связывает публичное описание блока с Python-классом проверки настроек:

- `definition` отправляется для frontend;
- `config_model` - Python-класс, который backend вызывает для проверки.

`BlockRegistry` - хранит все записи в словаре `(block_type, version) -> BlockSpec`. Один тип блоков может иметь несколько версий. Повторная регистрация одинаковой пары типа блока и версии вызывает `ValueError`.

- `get()` - ищет указанный блок в передаваемой спецификации `specs`
- `definitions()` - возвращает копии публичных описаний блоков из domain.BlockDefinition

`builtin_registry()` - заполняет каталог всеми определениями блоков

### validation.py

`contract_errors()` - проверяет входной и выходной порт:
1) Сравниваются базовые типы портов: `if output.type != input_port.type: ...`
2) Проверяется количество значений:
```python
if output.cardinality == "collection" and input_port.cardinality == "single":
    ...
```
Разрешены все варианты, кроме `collection` -> `single`
3) Проверяется, может ли необязательный выход гарантировать обязательный вход, сравниваются capabilities.
4) Список требований трактуется как набор допустимых значений. Например:
```python
# Производитель:
features = ["numeric", "categorical"]

# Потребитель:
features = ["numeric"]
```

Соединение отклоняется, т. к. потребитель не заявляет о поддержке категориальных признаков

`validate_workflow()` - проверяет весь граф за неколько проходов:

1) Проверяет узлы: не повторяется ли UUID, зарегистрирована ли указанная пара типа и версии, подходит ли конфигурация соответствующей Pydantic-модели
2) Проверяет рёбра: нет ли точного дубликата соединения, существуют ли оба узла, существует ли выходной порт у источника, существует ли входной порт у получателя, совместимы ли контракты.

Для этого создаются вспомогательные структуры:
| Переменная | Для чего нужна |
|---|---|
| `incoming` | Список соединений каждого входного порта |
| `adjacent` | Какие узлы зависят от данного узла |
| `degree` | Сколько входящих зависимостей у узла |
| `touched` | Какие узлы участвуют в связях |
| `seen_edges` | Обнаружение повторных соединений |

3) Проверяются обязательные входы и ограничения single. Полностью изолированные узлы получают предупреждение, но не запрещаются.
4) Выполняетя топологическая сортировка (`while queue:`) - она находит порядок, при котором каждый производитель располагается раньше своих потребителей:
   - Берутся узлы без входящих зависимостей;
   - Полученные узлы добавляются в результат;
   - Уменьшается число оставшихся зависимостей у следующих узлов;
   - Процесс повторяется.

Если обработать все узлы не удалось, значит, в графе есть цикл, который на данный момент не поддерживается.

Финальный результат считается **успешным**, если нет сообщений уровня `error`. Предупреждения не блокируют успех. `STATIC_ONLY` добавляется всегда для обозначения предела выполненной проверки.

### golden_path.py

Программно собирает пример графа:
`rows` содержит узлы, их настройки и координаты. `connections` - связи портов.
Затем из этих списков создаются объекты `WorkflowNode` и `WorkflowEdge`.

### main.py

Содержит все эндпоинты и создаёт FastAPI-приложение с реестром блоков
